# A/B 共享契约 v1

A 维护 src/tax_harness/contracts.py、ports.py 和 schema.sql。B 可以直接 import 契约，按 Protocol 实现模块。GET /api/contracts 提供 JSON Schema，Swagger 仅列出当前实际可用的 HTTP 入口。

| 数据结构 | 约定 |
|---|---|
| Scope | 用户、企业、明确月份，必须先经 authorize 核验；构造 Pydantic 对象本身不表示已授权 |
| MessageRequest | 请求和会话 ID、企业、文本；month 可空以支持追问，用户身份由应用层取得 |
| TurnResponse | 请求 ID、任务状态、回复、待办、操作 ID、引用 |
| ToolResult | succeeded/pending/failed/unknown；失败和未知必须带 Error |
| Error | code、message、retryable；未知写入不能仅凭 retryable 自动重试 |
| Citation | doc_id、name、version、entry，名称用于符合材料包的引用要求 |
| InvoicePatch | 仅 purpose 与 note；省略字段保持原值，显式 null 表示用户要求清空；使用 exclude_unset=True |

B 的 MemoryStore 提供 list_active/create/correct/delete/filter_history/is_current。默认记忆限定当前用户与企业；用户明确要求跨企业偏好时才使用 user_wide。个人长期偏好的管理根据归属授权，和修改发票的权限分开判断。更正或删除检查 expected_revision，返回新的 MutationReceipt，并过滤原始历史中失效内容。删除保留必要失效标识，后续 list_active 排除失效记录。

RuleStore 提供 search/add_version/deactivate/verify_citation/is_current。search 先按企业、生效时间、有效状态过滤，再检索文本。添加和停用通过共享修改协调机制执行，测试阶段规则管理入口仅授予 U001，后续管理身份机制另行配置。add_version 的规则企业必须与已授权 Scope 一致。is_current 必须同时检查 active 和 revision。RuleHit.effective_from 使用 ISO 日期，导入端验证真实日期。

RevisionRef 的 memory identifier 为 memory_id。rule identifier 统一为 JSON 数组字符串 `[doc_id, version, enterprise_id, entry]`，采用 json.dumps(..., ensure_ascii=False, separators=(',', ':'))。范围和修订变化后执行器必须重新取值，不能沿用旧 ContextBundle。

entry 使用稳定的短条目标识，例如 `1` 或 `purpose-required`，正文放在 content 中。共享请求与返回示例见 contracts.examples.json，示例已通过对应 Pydantic 类型构造验证。

模块错误统一用 PermissionError 表示越权，KeyError 表示找不到对象，ValueError 表示参数错误；修订冲突使用 RevisionConflict。HTTP 层随后统一映射到 Error，当前 /api/scope 已返回 403 Error。B 读取任务或消息时核对任务归属；不能仅依靠传入的 ID。

ContextBuilder 由 A 实现。输入为 ContextRequest，B 提供有效记忆、规则与筛选后的历史。输出 ContextBundle 包含实际模型消息、工具定义、来源修订、删减消息 ID 和用量计数方式。model/provider 的输入适配随后完成；字符估算必须在 token_count_method 如实标识，不能伪称精确 token。凭据不进入快照。

B 的数据导入模块负责逐表读取及数量核对，A 负责表结构和映射。原始工作簿有标题和说明行，应寻找真实表头，排除非明细行。

| Excel 表/字段 | 数据库映射 |
|---|---|
| 企业与用户 | 初始化已内置 C001/C002 与 U001/U002；导入时核对而不改写权限 |
| 发票 企业编号、发票编号 | invoices.enterprise_id、invoice_id 复合主键 |
| 开票日期、销售方名称、项目名称（票面） | invoice_date（ISO 日期）、seller、item_name |
| 价税合计（元） | amount_cents，用 to_cents(str(value)) 转换 |
| 用途、备注 | purpose、note，空单元格保存 NULL，纯空白的业务判定使用 strip |
| 银行 企业编号、流水编号 | bank_transactions.enterprise_id、transaction_id 复合主键 |
| 交易日期、收支方向 | transaction_date，收入映射 income，支出映射 expense |
| 金额（元）、对方名称、备注 | amount_cents、counterparty、note |

导入后核对发票 40 条、流水 48 条，每企业每月 10/12 条，金额分别汇总。规则使用正文材料，不把 Excel 汇总复制成查询结果。导入器默认拒绝覆盖已有业务数据，重置使用明确操作或新数据库文件。所有写入使用 database.write()，失败整批回滚。

建议 B 建立 tax_harness/memory.py、rules.py、import_data.py 和网页资源目录。B 首次交付包含可导入的模块、模块测试、初始化命令和导入核对结果；A 负责组合根、权限及共享数据库注入。双方使用同一契约版本，以同一基础提交开始工作。

当前 B 已实现 memories 与 rules 路由和工作台。B 路由使用 `X-Demo-User` 请求头及 `enterprise_id`、`month` 查询参数。DELETE 偏好通过查询参数提交 `expected_revision`，停用规则在查询参数提交 `version`，正文提交 `expected_revision`。GET /api/rules 无 `query` 时返回版本与启用状态，有 `query` 时返回适用命中项。按当月末日期选择每个规则编号最新生效的启用版本，同一企业的同一规则在相同生效日仅允许一个启用版本。

GET /api/workbench/records 返回当前用户、企业、月份的发票和流水数量，以及最多 30 条任务、操作、事件和用户来源消息。A 的执行器从 `app.state.memory_store` 和 `app.state.rule_store` 取得同库实现。网页在 OpenAPI 出现 POST /api/messages 后启用对话发送。偏好新增需要选择当前范围内已有的用户消息。记忆更正和删除会排除原始来源消息，来源记录仍可在授权范围内查看。

B 的写方法自行使用共享 Database 实例开启事务，执行器应在自己的数据库写事务结束后调用这些方法。需要在业务保存前核验来源时，使用两个 Store 的只读 is_current。

## A2 只读业务接口

A 的执行器通过 `app.state.business_reader` 使用 `BusinessReader`。以下 HTTP 入口同样使用 `X-Demo-User`、`enterprise_id` 和 `month`。每个入口都先校验企业的查看权限，再从当前 SQLite 明细读取数据。

| 路由 | 附加筛选 | `ToolResult.data` |
|---|---|---|
| GET /api/invoices | `invoice_id` 精确匹配，`seller` 和 `item_name` 按字面子串匹配 | `records`、`invoice_count`、`invoice_cents` |
| GET /api/bank-transactions | `transaction_id` 精确匹配，`direction` 为 `income` 或 `expense` | `records`、`bank_count`、`income_cents`、`expense_cents` |
| GET /api/invoices/{invoice_id} | 当前企业及月份内的发票编号 | 单张发票字段，外层 `object_id` 为发票编号 |

汇总针对筛选后的全部记录，以整数分返回。收入、支出分别相加，均为正数口径。列表成功无记录时，`records` 为空数组，数量与汇总均为零。单张发票在当前范围内未找到时返回 404，越权返回 403，SQLite 查询失败返回 500 和 `tool_failed`，缺少月份返回 422。服务层沿用 `PermissionError`、`KeyError` 和数据库异常，HTTP 层负责映射。

验收直接使用 B 导入的 v1.1.0 数据库启动 Uvicorn。C001 与 C002 在 2026 年 8 月和 9 月的四组数量及三项金额全部与工作簿说明页一致。实际 HTTP 请求还核对了 U002 的查看范围、同号 F001 的企业隔离、错月份 404、无记录和缺月份。自动测试覆盖数据库故障与接口筛选，共 32 项通过。

## A3 保存、操作查询与任务关闭

| 路由 | 请求与结果 |
|---|---|
| PATCH /api/invoices/{invoice_id} | `InvoiceSaveRequest`，返回含操作编号、已核验记录和修改前后值的 `ToolResult` |
| GET /api/operations/{operation_id} | 按用户、企业和月份查询记录。`confirmed` 返回当时的回查快照，`prepared` 和 `dispatched` 返回 `pending`，`unknown` 返回 `unknown` 与 `unknown_result` |
| PATCH /api/tasks/{task_id}/status | `TaskCloseRequest`，`status` 为 `completed` 或 `cancelled`，同时提交任务当前 `expected_revision` |

三个路由继续使用 `X-Demo-User` 请求头及 `enterprise_id`、`month` 查询参数。保存先校验写权限，再校验发票与任务范围。`expected_revision` 使用 `GET /api/invoices/{invoice_id}` 返回的发票修订。补丁省略的字段保留原值，显式 `null` 清空字段。第一次显式保存可以在该企业没有未完成任务时创建请求指定的任务。已有未完成任务时复用其 `task_id`。若任务已绑定发票，保存目标须与该发票一致。

```json
{
  "task_id": "a3-task",
  "session_id": "a3-session",
  "request_id": "a3-save-1",
  "operation_id": "a3-operation-1",
  "expected_revision": 1,
  "patch": {"purpose": "办公资料", "note": "已核对"}
}
```

同一次重试保留全部请求字段，读取原操作结果。相同编号携带不同内容、发票修订过期或存在未决写入时返回 409。新修改使用新的请求和操作编号，保存内容与现值一致时记录核验结果，发票修订保持原值。`request_id` 标识本次保存，后续执行器可从对话请求派生独立、稳定的保存请求编号。A 的执行器通过 `app.state.business_writer` 调用 `BusinessWriter`，由执行器在调用前确认用户的明确修改意图与上下文来源修订。

请求、操作、发票修改、回查和审计记录在同一 SQLite 事务中提交。需要获取当前发票时使用单张发票查询，操作查询保留的是该次保存的历史快照。`unknown` 状态下，同一请求只能取得待核验结果。同票据的新写入及关联任务的完成、取消均返回 409，直至操作核验结束。

验收通过 SQLite 备份创建 B 的 v1.1.0 临时副本，实际启动 Uvicorn 测试。已验证同号 F001 隔离、U002 写入拒绝、错月份与非法字段拒绝、保存后独立读回、相同请求重放、新请求甲→乙→甲、审计写入故障后的完整回滚。在副本注入持久化 `unknown` 状态后，已验证重试无额外修改、冲突写入被拒绝、完成和取消均受阻。恢复核验记录后任务可关闭。B 源库验收前后 SHA-256 一致，自动测试共 41 项通过。

## A4 模型适配、执行循环与上下文

`POST /api/messages` 接收 A1 的 `MessageRequest`，从 `X-Demo-User` 获取身份，返回 `TurnResponse`。同一请求重放已记录的回复，参数不同时返回冲突。未指定月份时优先恢复当前企业的未完成任务范围，否则提示补充月份。该企业有其他月份的待办时，旧月份的查询轮按只读处理。初赛进程同一时刻处理一轮对话，忙碌时返回冲突并允许客户端复用原请求编号重试。

模型输出结构化 JSON 决策，执行器只接受已注册工具。查询由 A2 执行，规则与有效记忆从 B 读取，失效历史经过 B 过滤。每轮至多六次模型决策，格式错误或无效工具可在剩余步数内修正。上下文保留范围、任务、待办和当前输入，优先纳入本轮工具结果，再加入适用规则、有效记忆和近期历史。预算采用序列化 UTF-8 字节估算，超限先缩减明细与历史，汇总金额保留。日志记录实际输入、来源、模型动作和工具结果，排除模型密钥。引用需存在于本轮实际依据中且当前仍适用。回答中的银行收入或支出金额必须来自本轮覆盖该方向的流水查询；只查收入时，筛选结果里的支出 0 不能当作全月支出，程序会驳回并要求补查。回答若声称旧提案仍待确认，但这一步不会留下待确认提案，同样驳回。

模型提出用途或备注修改后，执行器先核对目标发票编号。编号必须出现在用户本轮或同一企业月份的历史输入中，或与任务已确认的 `object_id` 一致。只在查询结果里出现的编号不能单独成为目标；否则不生成提案，改为追问编号。通过后展示企业、月份、发票和精确修改值。同一会话下一次明确回复 `确认保存` 才会触发 A3。回复 `取消保存` 可取消尚未执行的提案。其他消息结束旧提案的确认资格，可在该轮重新生成提案。保存前复核记忆、规则及发票修订。操作和请求编号由提案稳定派生，A3 事务提交后由 A4 再独立读回发票。结果未确认时保留待核验信息。

HTTP 适配器需要设置 `HARNESS_MODEL_ENDPOINT`、`HARNESS_MODEL_NAME`、`HARNESS_MODEL_KEY`。端点是完整的 Chat Completions 兼容地址，模型在消息中获取工具定义并以 `choices[0].message.content` 返回 JSON。整段内容若只包在一个 `<tool_call>` 或 Markdown JSON 代码块里，解析前先去掉这层包装，再按原 schema 校验；缺字段、多余字段和其他正文仍然拒绝。密钥只放在进程环境，不写入代码、日志或追踪。`HARNESS_INPUT_BUDGET` 默认 12000。环境变量由启动进程提供，程序不另读 `.env`。缺少模型配置时，需要推理的请求返回 503。已有任务恢复、确认和操作查询仍可使用。

**本机 HTTP 模型替身验收通过。** B 的 v1.1.0 SQLite 备份副本通过实际 Uvicorn 与本机 HTTP 模型替身跑完查询、规则引用、使用 B 偏好、追问、补充、确认、保存和回查。甲企业 9 月结果为发票 9622.06 元、银行收入 13000.50 元、支出 7180.74 元，并引用 R002 2.0。F001 确认前未改变，确认后用途和备注与独立查询一致。重复确认只有一笔操作，跨会话确认和越权被拒绝。六次模型请求的实际消息与审计快照一致，B 源库 SHA-256 一致。

**赛事真实模型待验证。** 本机未配置赛事端点、模型名称和密钥。替身结果用于验收执行循环、适配协议和业务数据流。

## A5 范围切换、任务恢复与写入核验

`GET /api/tasks/active` 使用 `X-Demo-User`、`enterprise_id` 和 `month`，返回该用户在所选企业的未完成任务。`matches_month` 表示所选月份是否匹配任务月份。匹配时可查看未决操作编号。没有未完成任务时返回 `{"task":null}`。

切换企业后按新企业取得任务、历史、记忆和规则。选回原企业及月份，在新会话发送 `继续任务` 可恢复同一个任务。待确认修改会重新展示并绑定新会话，用户看过后再回复 `确认保存`。如果选了同企业的其他月份，普通查询按只读执行，原任务仍保留。要开始该月的新任务，先使用任务状态接口完成或取消原任务。数据库的用户与企业唯一约束继续覆盖 `running`、`waiting_user` 和 `blocked`。

模型 HTTP 超时由 `HARNESS_MODEL_TIMEOUT` 控制，默认 90 秒。模型决策请求没有业务写入，读超时会再试一次；得到响应后的格式错误不重试。确认保存不调用模型，仍用提案派生的操作编号和独立回查，重试不会多写一笔。超时后的对话回复只说明本次没有得到可用结果，请求记为失败；没有待办时任务保持进行中，不记为已完成。已有待补充事项或待核对提案仍保留。之前展示的修改需要通过 `继续任务` 重新核对后才能确认。同一个已响应请求编号可重放历史回复，想重新发起模型处理时使用新的请求编号。

新请求在保存前持久化任务修订和关联操作编号。重启后以相同请求编号及正文重试，先查原操作。若原操作已提交，则独立回查并恢复回复；若尚无操作且任务修订一致，则继续原请求。若任务已变化，则拒绝盲目重放。早于 A5 的中断请求缺少检查点，需按任务和操作记录核验。

未决状态下，`继续任务` 和保存确认返回待核验操作。冲突写入、完成和取消继续被阻止。`POST /api/operations/{operation_id}/reconcile` 复用同一范围和写权限，仅当原保存请求的持久化回执及当前发票回查完整匹配时恢复 `confirmed`。凭据缺失或不一致时保留原状态。核验更新操作状态和审计记录。

**本机 HTTP 模型替身验收通过。** 使用 B 的 v1.1.0 SQLite 备份副本和实际 Uvicorn，验证了企业间上下文隔离、同企业切月只读、超时后跨会话恢复、重启后按原请求回查、未知写入阻塞及有凭据时解除阻塞。提交后响应中断采用副本中的故障注入。重启后移除替身配置，仍可按原请求查回已提交结果。最终只有一条保存操作及一条保存事件。B 源库 SHA-256 一致。自动测试共 57 项通过，额外覆盖提交前中断、同企业单未完成任务与回查不匹配时继续阻塞。

**赛事真实模型待验证。** 本机未配置赛事模型端点、名称和密钥。上述结果记录为本机替身与业务恢复验收。

## A6 工作台联调

`GET /api/tasks/{task_id}` 返回待办 `question`、绑定发票 `object_id`、`revision`、`status` 和 `has_proposal`。`PATCH /api/tasks/{task_id}` 接收 `TaskCorrectionRequest`，提交刚读到的 `expected_revision`，以及要修改的 `question` 或 `object_id`。省略的字段保留，传 `null` 清除。两个入口都用 `X-Demo-User` 及 `enterprise_id`、`month`，并核对任务所有者。修订过期、任务已关闭或存在未决操作时拒绝修改。成功后旧提案失效，已保存的操作记录仍可查询。工作台从「运行记录」进入更正待办。

模型返回普通 `answer` 时默认保留原追问。只有模型明确返回 `resolved_pending_question: true` 才能通过该类决策关闭原追问。工作台对话展示剩余事项、已核验规则引用和操作编号。

`check_invoice_purposes` 使用现有发票查询筛选字段，返回 `missing_count`、缺用途明细及规则引用。初赛范围是 2026 年 9 月，甲企业采用 R002 2.0 的全部发票口径，乙企业采用 R003 1.0 的大于或等于 1000.00 元口径。用途为空或纯空白均算缺项。若当前生效版本超出程序已核对的版本，工具返回缺少可执行规则，请先核对版本。规则检索本身仍可返回当月适用的新版本。
