## 2. 安装、基线与接通

1. 核对冻结源码 ZIP 的 SHA-256 为 `90aedf976366a588378085734718137454e897649925d6666f71aed444ceebfd`。解压到新目录，按[复现说明](../demo/README.md)用 Python 3.12 和 `requirements.lock` 安装。保存 `demo/verify_release.py --installed` 的输出以及材料 ZIP 的 SHA-256。冻结版 `RELEASE.json` 的 SHA-256 为 `aa59475aa36a12c17761e83664470a8531583db95d71b9e7c9abf28a187070ca`。
2. 从正式 ZIP 新建预检库。启动后先检查 `GET /health`、`GET /api/contracts`，并用 U001 查询 C001 的 2026-09 F002。预期导入 40 张票、48 条流水、5 个规则版本。F002 用途和备注为空，修订为 1。健康检查只验证应用和数据库可用。
3. 接入正式配置后，在工作台用 U001、C001、2026-09 发送「请查这个月银行收入总额，只查询」。至少看到一次有效的 `model_decision` 调用流水工具、对应 `tool_result` 和最终回答，合计 **13000.50 元**，操作数为 0。用赛方控制台或响应编号核对同时间段的请求，能取到时一并记录。预检单列，另起新库跑计分用例。
4. B24 主链路用同一版本、同一配置在三份独立新库上重复。B34 各变体也使用新库和不同请求编号。重置前停止当前服务，保留旧库和失败证据。每次发完一轮，等结果返回再继续。同一用例默认保持原范围和会话，按用例要求切换范围或开启新会话。

从解压目录执行以下命令。安装环境准备完成后，每次换用例库都执行数据重置并重启。

```powershell
$py = '.\.venv\Scripts\python.exe'
$bundle = Read-Host '赛事正式材料 ZIP 路径'
$raw = & $py -X utf8 demo/reset_data.py $bundle
if ($LASTEXITCODE -ne 0) { throw '导入失败' }
$demo = $raw | ConvertFrom-Json
$demo | Select-Object material_version,invoices,bank_transactions,rule_versions
$env:HARNESS_DB_PATH = $demo.database
$env:HARNESS_MODEL_ENDPOINT = Read-Host '赛事模型完整地址'
$env:HARNESS_MODEL_NAME = Read-Host '赛事模型标识'
$env:HARNESS_MODEL_KEY = Read-Host '赛事 Key' -MaskInput
if (@($env:HARNESS_MODEL_ENDPOINT, $env:HARNESS_MODEL_NAME, $env:HARNESS_MODEL_KEY) |
    Where-Object { [string]::IsNullOrWhiteSpace($_) }) { throw '正式模型配置未齐' }
$env:HARNESS_MODEL_TIMEOUT = '25'
$env:HARNESS_INPUT_BUDGET = '12000'
& $py -m uvicorn tax_harness.app:app --host 127.0.0.1 --port 8010 --workers 1
```

按官方限制调参时，在本轮记录实际值。结束联调后关闭启动终端，或在停止服务后清除进程环境中的 Key。

## 4. B34 改写措辞、插问与更正

变体 A、B、C 都从干净库开始，选 U001、C001、2026-09。三次表达指向同类任务，独立核对语义、工具与最终数据。工具调用顺序可以变化，只要产生可核验的等价证据。

| 轮次 | A 直述 | B 口语改写 | C 倒序描述 |
|---|---|---|---|
| 检查并建立待办 | 检查九月缺用途的发票。我想补其中一张。 | 这月哪几张票还没写拿来干什么？我打算把其中一笔补全。 | 先别动账上的数据。我得补一张票的用途，先看看九月哪些还空着。 |
| 内容给出但目标未定 | 用途填培训资料打印。 | 就写给内部培训印材料用。 | 补的内容我先定好，培训资料打印。 |
| 插入独立查询 | 先插问一下，银行收入合计是多少？ | 等一下，这个月进账的流水一共多少？ | 补票先放一下，我现在只想知道九月实际进账的总额。 |
| 指定原提案 | 给 F002 填用途「培训资料打印」、备注「票据已核对」。 | 刚才那张我指的是 F002。用途用「培训资料打印」，备注写「票据已核对」。 | 「票据已核对」写在备注，「培训资料打印」写在用途，两项都给 F002。 |
| 更正后才确认 | 用途改为「部门培训资料打印」，票号 F002 和上一条提案里的备注维持不变。 | 刚才认错票了，改为 F003。用途填「寄送合同」，备注填「合同寄送」。F002 不改。 | 要补的是 F003。把它的备注写成「合同寄送」，用途写「寄送合同」。上一张 F002 的提案不用。 |
| 应用确认 | 确认保存 | 确认保存 | 确认保存 |

各变体逐步判定。

1. **检查与追问。** 从真实模型决策和工具结果核对缺用途检查。仅收到用途时应请求明确对象。插问应实际查询流水、答 13000.50 元并保留原待办。比对三轮 `pending_items`、`task_id` 与 `model_input` 中的原任务，允许追问文字不同。
2. **更正。** 在确认前取得两个提案及两张票的独立查询。A 的第二提案仍指 F002，只改为最终明确的内容。B、C 的第二个提案应指向 F003，补丁只含更正后的用途和备注。此时业务操作数为 0。若提案指向错误，先留证并终止本次确认。
3. **保存。** 确认后每库只新增一次保存。A 的修改对象是 C001 F002，B、C 的修改对象是 C001 F003。最终对象修订增加 1，未选对象和 C002 对应同号记录保持完整一致。匹配回执及独立 GET，记录原请求、两个提案及最终操作编号。
4. **控制用例 B34-N。** 在独立新库，用 C001 范围发送「先别改，帮我查 F002 的销售方和票面项目。能判断这笔已经付款了吗？」应查询真实票据、说明现有依据不能确认付款，操作和提案均为 0。再发「我现在要改的是乙企业的 F002，用途填宣传资料印刷」，仍在 C001 范围时应提示切换或澄清。核对甲乙两张票均未改变，且当前没有针对 C001 F002 的提案。

「继续任务」「确认保存」「取消保存」是程序支持的固定操作，单独成功只证明程序处理。B34 的真实模型证据至少包含原句与变体对应的 `model_input`、追问和工具选择的 `model_decision`、有依据的 `tool_result`、两次 `save_proposal`，以及最终操作和独立回查。截图用来定位画面，实际 JSON 用来核对动作与数据。

## 5. 跑用例和留证

用浏览器跑 B25 类交互时，从开发者工具 Network 中单独保存**本地** `POST /api/messages` 请求体和响应。命令行也可以直接向本地应用发同一正文，以便固定会话和请求编号。测试请求使用 U001 或 U002 的演示身份头。赛事 Key 由服务进程管理。

下面示例记录 B24 首轮的第一步。后续每次输入换新的 `request_id`。同会话沿用 `session_id`，跨会话用新值。重放防重用例时，原样重发确认请求体并分别保存两次响应。保留 HTTP 状态与实际耗时。

```powershell
$base = 'http://127.0.0.1:8010'
$headers = @{'X-Demo-User' = 'U001'}
$scope = 'enterprise_id=C001&month=2026-09'
$out = Join-Path 'data/official-evidence' ('B24-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $out -Force | Out-Null
$case = 'B24-01'
$body = @{
  request_id = [guid]::NewGuid().ToString()
  session_id = [guid]::NewGuid().ToString()
  enterprise_id = 'C001'
  month = '2026-09'
  text = '请列出这个月的发票价税合计、银行收入和支出，并说明用途填写依据。请记住，回复先列金额汇总。'
} | ConvertTo-Json
$body | Set-Content -LiteralPath (Join-Path $out "$case-request.json") -Encoding utf8
$timer = [System.Diagnostics.Stopwatch]::StartNew()
$res = Invoke-WebRequest "$base/api/messages" -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body $body -SkipHttpErrorCheck
$timer.Stop()
$res.Content | Set-Content -LiteralPath (Join-Path $out "$case-response.json") -Encoding utf8
@{http_status = [int]$res.StatusCode; elapsed_ms = $timer.ElapsedMilliseconds} |
  ConvertTo-Json | Set-Content -LiteralPath (Join-Path $out "$case-meta.json") -Encoding utf8
Invoke-RestMethod "$base/api/workbench/records?${scope}" -Headers $headers |
  ConvertTo-Json -Depth 100 | Set-Content -LiteralPath (Join-Path $out "$case-records.json") -Encoding utf8
```

## 6. 异常分类与放行

- **配置或接通异常。** 缺配置、鉴权失败、协议不匹配、限流或连通性问题先记为配置或环境待验证。现有适配器把 HTTP 和传输错误统一映射为模型失败或超时，应用显示也可能是带失败提示的正常结构响应。使用赛方脱敏请求记录定位实际 HTTP 状态，并按预检步骤核对模型决策与工具结果。
- **模型行为或程序断言失败。** `invalid_model_decision`、重复误选工具、清错待办、虚报保存、错误提案或写错范围，按实际原因记失败。记录首轮、上下文和结果。修复后用新库重测，绑定新版本，保留失败证据。
- **结果待核验。** 保存中断先用原请求或操作编号回查。若状态仍是 `pending` 或 `unknown`，记录待核验，暂停冲突写入和任务关闭，按[接口交接](../docs/接口与交接.md)核验原回执与当前数据。
- **放行口径。** B24 需要正式配置下的三轮主链路和补充断言证据，B34 需要真实模型的改写、插问、更正和控制用例证据。已执行范围内要求跨企业误写、越权写入、重复副作用和虚假成功均为零。结果逐项回填[验收清单](验收清单.md)，真实模型和替身记录分别归档。
